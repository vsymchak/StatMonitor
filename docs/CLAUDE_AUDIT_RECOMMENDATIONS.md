## 0. Резюме: 12 головних проблем

| # | Серйозність | Суть |
|---|---|---|
| 1 | 🔴 | Пароль БД і адмін-ключ жорстко прописані в коді та скриптах (один і той самий рядок у `dashboard.py`, `bot.py`, `scripts/*.py`); адмін-ключ має «вшитий» fallback, який приймається завжди |
| 2 | 🔴 | Реальні гроші (SX Bet, USDC) торгуються автоматично без жодних запобіжників: Stop-Loss/Max Exposure/кореляції діють лише на UAH-банк |
| 3 | 🔴 | Fail-open логіка ШІ: якщо Gemini недоступний або модель потрапила в `EXHAUSTED_MODELS`, `confidence=None` і ставка проходить без фільтра |
| 4 | 🔴 | Зіставлення команд для SX Bet нормалізує «Real Madrid» і «Atlético Madrid» до однакового токена, «Manchester City/United» теж; у дербі можлива ставка на неправильну команду |
| 5 | 🔴 | Чотири незалежні шляхи запуску пайплайну (Render, GitHub Actions, Cloudflare, локальний демон) без взаємного блокування. Публічний `GET /trigger` на Render без автентифікації |
| 6 | 🟠 | Автоматичний розрахунок тенісу за рахунком у сетах: фори/тотали (у геймах) рахуються неправильно. Це і є причина ручних «хотфіксів» для ставки #56 |
| 7 | 🟠 | Реальний леджер: read-then-insert без блокування, `WITHDRAWAL` з клемпом ламає тотожність `SUM = balance`, корекція результату не відкочує запис у леджері |
| 8 | 🟠 | «0.10×Kelly» для реального банку — неправда: при наявному `kelly_pct` реальна ставка = % paper-ставки (до 5 %), параметр `fraction` ігнорується |
| 9 | 🟠 | Walkaway Odds — не беззбитковий поріг, а ≈ −2 % від поточної ціни за евристикою; `fair_prob` (de-vig Pinnacle) у пайплайні не використовується |
| 10 | 🟠 | Бектест «Золотий стандарт Confidence ≥ 8» зроблено на ~4 днях і десятках ставок з перебором 170 конфігурацій: статистично не значущий (p-hacking) |
| 11 | 🟠 | Dead code у критичних місцях: ECO/CRITICAL режими лімітера ніколи не вмикаються; `scheduler_run`-heartbeat ніхто не пише (Smart Gate завжди «пропускає»); налаштування ліг у дашборді не діють на демон; вимкнуні тенісні ліги все одно опитуються |
| 12 | 🟠 | Міграційний розрив: `system_errors`, `sx_settings`, `real_profit_uah` не мають міграцій; fallback-DDL не виконується, якщо міграції «застосовані» |

## 1. Безпека

### S-01 🔴 Секрети в коді
- `scripts/spec42_grid_search.py`, `scripts/inspect_conf8_odds.py`: повний рядок підключення до Supabase з паролем (роль `postgres`).
- `dashboard.py`: `secret_key = ... or "<той самий пароль>"` і перевірка `query_key == "<той самий пароль>"` — адмін-доступ приймається навіть якщо `SECRET_KEY` у Secrets інший.
- `statmonitor/bot.py::cmd_run_now`: `secret="<той самий пароль>"`.
- **Наслідок:** пароль БД = адмін-ключ дашборда = секрет вебхука. Компрометація одного — повний доступ до БД і керування. Пароль уже в git-історії.
- **Виправлення:** негайна ротація пароля БД і `SECRET_KEY`; видалити всі літерали; `git filter-repo`/BFG для історії; перейти на `os.environ[...]` без дефолтів (падати при відсутності).

### S-02 🔴 Адмінка дашборда
- Один спільний пароль, порівняння не у сталий час, `.lower()`-порівняння послаблює його, немає ліміту спроб.
- Ключ у query-параметрі (`?key=`): навіть із подальшою санітизацією він встигає потрапити в логи проксі та `Referer`.
- **Виправлення:** `hmac.compare_digest`, прибрати query-логін; використати вбудований `st.login` (OIDC) або Cloudflare Access перед Streamlit; журнал спроб входу.

### S-03 🔴 Принцип найменших привілеїв
- Дашборд (публічний Streamlit Cloud) отримує DB URL з правами `postgres` і приватний ключ SX Bet (`SXBetClient()` у `get_sx_bet_dashboard_data`, кнопка «перенести на SX Bet» підписує ордери прямо у веб-процесі).
- **Виправлення:** ролі в БД (`app_reader` для дашборда — SELECT; `worker_rw` для воркера); приватний ключ лише у воркері; дії адміна з дашборда — через таблицю команд `admin_commands` (insert), які виконує воркер.

### S-04 🔴 Публічний `GET /trigger` (`render_service.py`)
- Без автентифікації, state-changing GET, потік на кожен запит без обмеження → спалювання квоти Odds API/Gemini, дублі ставок, DoS.
- Додатково: демон і `/trigger` запускають `run_pipeline` паралельно (див. A-01).
- **Виправлення:** `POST` + секрет у заголовку (`hmac.compare_digest`), `threading.Lock`/advisory lock (single-flight), rate-limit; `/healthz` залишити публічним.

### S-05 🟠 Telegram-бот: fail-open і слабка авторизація
- `is_authorized`: `if not TG_CHAT_ID: return True` — без змінної бот відповідає кому завгодно (включно з `/settle`, `/edit_odds`).
- Перевіряється `chat.id`, а не `from.id`: у груповому чаті авторизований будь-який учасник.
- `--once`: `offset` не підтверджується (loop виходить після першого `getUpdates`), тож команди повторно виконуються при кожному запуску до 24 год. Для `/settle` і `/edit_odds` це небезпечно.
- **Виправлення:** fail-closed; allowlist `from.id`; після обробки викликати `getUpdates(offset=last+1)`; зберігати offset у БД.

### S-06 🟠 Витік токенів у логах
- `notifier.py`: `print(f"TG msg err: {e}")`. Виняток `requests` містить URL з `/bot<TOKEN>/`.
- `ai.py`: ключ Gemini у query-рядку `?key=` (виняток проковтується, але ключ видно в проксі/логах).
- **Виправлення:** заголовок `x-goog-api-key`; логувати `type(e).__name__` і маскований текст; глобальний фільтр логів, що вирізає `bot\d+:[\w-]+` та `key=...`.

### S-07 🟡 HTML-інєкції в дашборді
- `st.markdown(..., unsafe_allow_html=True)` з даними з БД/зовнішніх API: `match_name`, `iss['title']`, `err.details` (містить фрагменти відповідей API). Назви матчів надходять від третьої сторони.
- **Виправлення:** `html.escape()` для кожної підстановки; хелпер `safe_html()`.

### S-08 🟡 Дашборд пише в БД при кожному рендері
- `fetch_data` виконує `UPDATE paper_bets` (хотфікси #56 і #76, округлення, авто-перерахунок реальних сум) з `autocommit=True` — навіть для гостей у режимі Read-Only.
- Хотфікс #76 при кожному відкритті сторінки перезаписує `pick_label/odds` активної ставки з `id=76`/Medvedev–Tiafoe — ручні правки скасовуються.
- Хотфікс #56 ставить `WON` без запису в леджер реального банку (а ставка реальна).
- **Виправлення:** прибрати з рантайму; перенести у разові міграції/скрипти з аудит-записом; дашборд — read-only.

### S-09 🟢 SQL
- `cold_archive.py`: `INTERVAL '{min_age_days} days'`, `LIMIT {batch_limit}` через f-string (числа, але краще параметри: `make_interval(days => %s)`).
- Динамічні імена колонок (`ai_txt`, `time_col`) беруться з `information_schema` — безпечно, але це симптом schema drift (див. D-04).

### S-10 🟡 Інфраструктура
- `requirements.txt` без піннінгу (`>=`), одна збірка для воркера і дашборда (Streamlit/Plotly на Render Free, pyarrow, matplotlib). Ризик OOM на 512 МБ і нерепродукована збірка.
- `scripts/place_live_bet.py` містить синтаксично некоректний код (відступи, невизначені `all_markets`, `m_hash_live`) і призначений для реальних ставок; `check_positions.py` вставляє захардкожену транзакцію в продакшн-БД.
- **Виправлення:** видалити/перенести в `tools/` із `--confirm` і dry-run за замовчуванням; `requirements-worker.txt`, `requirements-dashboard.txt`, `requirements-dev.txt` + lock (`pip-compile`).

## 2. Фінансова коректність та торгова логіка

### F-01 🔴 SX Bet без Circuit Breakers
`auto_sync_and_stake_from_paper` викликається з пайплайну (кожен цикл) і з дашборда. SPEC-36 (Stop-Loss 7 %, Exposure 20 %, кореляції) покриває лише UAH-банк у `real_bankroll.py`. Для USDC:
- немає денного ліміту втрат, ліміту сумарної експозиції, ліміту ставок на добу;
- немає глобального kill-switch;
- мейкер-ордери (`OPEN_ORDER`) не резервують баланс: `free_usdc` зменшується локально, але на біржі кошти не заблоковані, тож сумарні відкриті ордери можуть перевищити баланс.
**Виправлення:** таблиця `system_flags` (`trading_enabled`, `sx_autostake_enabled`), `evaluate_sx_risk_guardrails()` (дзеркало SPEC-36 в USDC), перевірка перед кожним ордером; автостейкінг вимкнений за замовчуванням, вмикається прапорцем.

### F-02 🔴 Fail-open ШІ-фільтра
- `analyze_gemini` проковтує всі винятки (`except: pass`), а `EXHAUSTED_MODELS.add(model)` при 404/429 діє до перезапуску процесу. У 24/7-демоні кілька хвилинних 429 назавжди вимикають моделі.
- Далі: `extract_confidence_score(None) → (None, None)`; `place_paper_bet(confidence=None)` пропускає ставку без фільтра (умова `elif confidence is not None`) → активна ставка (і реальна, якщо її перенесуть).
- **Виправлення:** `confidence is None` ⇒ shadow з причиною `AI_UNAVAILABLE`; TTL для `EXHAUSTED_MODELS` (наприклад, 10 хв для 429, 24 год для 404); логувати помилки Gemini в `system_errors`; повторні спроби з backoff.

### F-03 🔴 Хибне зіставлення команд (SX Bet)
`normalize_team_text` викидає «real», «united», «city», «fc»…. Тест фіксує `"Manchester City FC" → "manchester"`. Наслідки:
- «Real Madrid» → `madrid`, «Atlético Madrid» → `atletico madrid`; `_teams_similar` проходить за підрядком.
- У дербі `match_direct` і `match_rev` одночасно істинні, а вибір сторони (`want_team`) робиться тим самим нечітким порівнянням → реальна ставка на іншу команду.
- Те саме: Manchester City/United, Inter/Inter Miami, Sporting/Sporting Gijón тощо.
**Виправлення:** таблиця `team_aliases(canonical_id, alias, sport)` + канонічні ID; для зіставлення — точний збіг канонічних ID, а нечіткий збіг лише для пропозиції; для реальних грошей — режим «propose → підтвердження» з preview (команда/час/лінія/коефіцієнт) у Telegram; заборона автоставки, якщо кілька кандидатів.

### F-04 🟠 «Taker» не реалізований
У `auto_sync_and_stake_from_paper` режими `TAKER` і `MAKER` відрізняються лише ціною й TTL: в обох випадках `POST orders-v3` з новим мейкер-ордером. **[перевірити]** за документацією SX Bet: виконання проти стакана робиться окремим fill-ендпоінтом, а розміщення ордера, що «перетинає» книгу, не гарантує миттєвого виконання. Також: `order_id = orderId or marketHash` (підміна ідентифікатора), відповідь API не перевіряється на `status == success`.
**Виправлення:** реалізувати fill для TAKER; валідувати тіло відповіді; без `orderId` — не писати в `sx_bets`.

### F-05 🟠 Автобухгалтерія SX маскує помилки
`sync_sx_exchange_full`: будь-яка розбіжність ≥ 0.10 USDC між ончейн-балансом і розрахунковим автоматично записується як `DEPOSIT`/`WITHDRAWAL`. Помилка в розрахунку PnL, комісії чи повернення перетворяться на «депозит» і спотворять ROI/депозити. `get_proxy_usdc_balance` при помилці RPC повертає `0.0`, що не відрізняється від реального нуля.
**Виправлення:** повертати `None`/кидати виняток при помилці RPC; розбіжності записувати як `RECONCILIATION_DIFF` + алерт (не як депозит); депозити — лише з ончейн-подій/підтверджені вручну.

### F-06 🟠 Реальний леджер: атомарність
`record_real_transaction`:
1. Читає останній баланс і вставляє новий рядок без блокування → гонка двох записів (дашборд + бот + settle).
2. `WITHDRAWAL`: `new_balance = max(0, cur − amt)`, але `amount = −abs(amt)` → при клемпі `SUM(amount) ≠ balance_after` (порушує інваріант SPEC-38).
3. `ADJUSTMENT`: знак перевантажений («від'ємне = дельта, невід'ємне = абсолют»); `SET_BALANCE` до від'ємного значення неможливий.
4. `commit()` усередині функції ламає зовнішні транзакції: `manual_settle_bet` спочатку комітить `UPDATE paper_bets`, потім окремо пише леджер; помилка леджера лише друкується → ставка розрахована, леджер — ні (і навпаки в `settle_and_report` часткові коміти в циклі).
5. `settle_real_bet_in_ledger`: перевірка дубліката і вставка — не атомарні; немає `UNIQUE`-обмеження.
**Виправлення:** `020_ledger_integrity.sql` (`uq_ledger_bet_result`, `real_profit_uah`), `pg_advisory_xact_lock`, `Decimal`, заборона овердрафту при `WITHDRAWAL`, окремі типи коригувань.

### F-07 🟠 Корекція результату не відкочує леджер
`/settle` і `manual_settle_bet` не перевіряють поточний статус і дозволяють перерахувати вже розраховану ставку. Але `settle_real_bet_in_ledger` вдруге не запише (захист від дублів) → реальний леджер залишається зі старим результатом, паперовий — з новим.
**Виправлення:** при перерахунку створювати компенсаційний запис (`REVERSAL`); таблиця `bet_audit_log`; заборонити перерахунок без явного `--reopen`.

### F-08 🟠 Автоматичний розрахунок тенісу
`settle_and_report` будує рахунок із відповіді Odds API (`scores`) і викликає `eval_outcome(h_sc, a_sc)`. Для тенісу API віддає виграні сети (наприклад, 2:0). Фора/тотал у тенісі — у геймах (`Ф1 (-3.5)`, `ТБ 21.5`): при сетах 2:0 `Ф1(-3.5)` завжди «LOST», `ТБ 21.5` — «LOST». **[перевірити]** формат `scores` для тенісу в Odds API.
**Виправлення:** для `tennis_*` авто-розрахунок лише для `h2h`; фори/тотали — ручна черга (`PENDING_MANUAL`) + нагадування в Telegram.

### F-09 🟠 Реальні ставки: розмір ≠ задокументований
`calculate_real_stake(kelly_pct=...)` бере `kelly_pct` (Quarter-Kelly 1–5 % від paper-банку) і застосовує його як частку реального банку, `fraction=0.10` ігнорується.
**Виправлення:** єдине джерело правди, масштабувати на `fraction/0.25`; оновити тести та документацію.

### F-10 🟠 Edge — евристика, а не перевага
`calculate_kelly_fraction`: `edge = 0.03 + drop_pct·0.30`; `calculate_novig_2way/3way` не викликаються в пайплайні; `estimate_walkaway_odds` без `fair_prob` дає `≈ 0.978·k`.
**Виправлення:** у `pipeline` збирати котирування Pinnacle (`odds_history`), рахувати `fair_prob` де-віг, `edge = k_offered·p_fair − 1`, `walkaway = (1+min_edge)/p_fair`.

### F-11 🟠 Fallback на коефіцієнт іншого ринку
`pipeline`: `real_odds = get_market_median_odds(..., fallback_odds=f["curr_k"])`. Якщо ШІ обрав ринок, відмінний від алерта, може піти фантомний коефіцієнт.
**Виправлення:** без цільового ринку — відсікати, валідувати вивід ШІ проти `odds_history`.

### F-12 🟠 CLV забруднюється
`capture_closing_lines`: другий виклик `get_market_median_odds(..., fallback_odds=bet_k)` записує `closing = bet`, `CLV = 0`, `beat_closing_line = False` як факт.
**Виправлення:** без закриття — залишати `NULL`; брати ціну закриття не старішу за 10 хв до старту.

### F-13 🟠 Ретроспективна зміна історії
`recalculate_historical_paper_bets` переписує вже розраховані ставки «заднім числом». Ставки мають бути append-only; корекції лише через `bet_audit_log`.

### F-14 🟡 Одноразове рішення
`active_events` виключає подію вічно після першого запису; `INSERT ... ON CONFLICT DO NOTHING` має перевіряти `cur.rowcount > 0`.

### F-15 🟡 Налаштування, що не діють
`min_confidence` з дашборда не передається у `place_paper_bet`; `btts` фільтрується у `fetcher`; `v_odds_alerts` відсікає `current_odds < 1.40` і `drop > -3%`.

## 3. Архітектура та надійність

- **A-01 🔴 Чотири шляхи запуску без взаємного виключення:** потрібен `pg_try_advisory_lock(hashtext('statmonitor_pipeline'))` у `run_pipeline`.
- **A-02 🟠 Smart Gate:** `scheduler_run` не оновлюється Watchdog-ом, демон має передавати `trigger_source="daemon"`.
