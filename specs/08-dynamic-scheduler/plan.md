# Технічний план реалізації SPEC-08: Динамічний планувальник

## 1. Архітектура компонентів

Створюється модуль `scheduler.py`, який:
1. Має чисті функції розрахунку розкладу, придатні для швидкого юніт-тестування без підключення до БД.
2. Інтегрується в `main.py` на етапі завершення циклу моніторингу.
3. Підтримує CLI-інтерфейс (`--show`, `--plan-only`).

```
                    ┌──────────────────────────┐
                    │     events (Supabase)    │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────▼─────────────┐
                    │  paper_bets (Supabase)   │
                    └────────────┬─────────────┘
                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────┐
│                    scheduler.py                             │
│  - cluster_events() -> об'єднання подій з delta < 25m       │
│  - build_schedule_points() -> генерація PRE_MATCH & SETTLE  │
│  - sync_schedule_to_db() -> запис у scheduler_plan          │
│  - format_schedule_tg() -> генерація блоку для Telegram     │
└──────────────────────────────┬──────────────────────────────┘
                               │
                ┌──────────────┴──────────────┐
                ▼                             ▼
       scheduler_plan (DB)          Telegram Summary Message
```

## 2. Алгоритмічні деталі

### `cluster_events(events, threshold_minutes=25)`
* Вхід: список подій із полем `commence_time`.
* Сортування за часом.
* Об'єднання в групи, якщо різниця між сусідніми подіями $\le 25$ хвилин.

### `build_schedule(events, pending_bets, now_utc)`
* Для кожного кластера подій формується точка `PRE_MATCH`: $T_{min} - 15 \text{ хв}$.
* Для кожної незавершеної ставки з `pending_bets`, чий матч розпочався або розпочнеться:
  точка `SETTLE` на $T_{kickoff} + 115 \text{ хв}$.
* Відкидаються точки, час яких вже минув більш ніж на 10 хвилин.
* Точки сортуються хронологічно.
