# Специфікація: Динамічний планувальник за часом матчів (SPEC-08)

## 1. Контекст та мета
Наразі система запускається за фіксованим розкладом у GitHub Actions (`.github/workflows/scheduler.yml`) кожні 2 години між 08:00 та 22:00 за Києвом.
Це призводить до двох основних проблем:
1. **Пропуск критичних коливань коефіцієнтів**: останні прогрузи перед самим свистком (за 15–30 хв до початку) пропускаються, якщо матч починається в середині 2-годинного інтервалу.
2. **Затримка розрахунку ставок**: матчі, що завершилися о 21:00 або 23:00, можуть очікувати розрахунку до наступного дня або до нічного запуску о 03:00.
3. **Неефективне використання квот**: під час пауз між матчами (наприклад, понеділок вранці) опитування раз на 2 години спалює ліміти API без нових подій.

**Мета SPEC-08**: Реалізувати динамічний генератор розкладу перевірок на основі реального часу старту матчів (`events.commence_time`) та активних ставок (`paper_bets`), який формує оптимальні точки запуску та відображає їх у звітах.

---

## 2. Бізнес-правила та алгоритм планування

### А. Типи контрольних точок (Trigger Types)
1. **PRE_MATCH (Передматчева фіксація)**:
   - Час: $T_{kickoff} - 15$ хвилин.
   - Мета: фіксація останніх котирувань, виявлення пікових прогрузів, остаточна ставка перед закриттям лінії.
2. **SETTLE (Розрахунок завершених ставок)**:
   - Час: $T_{kickoff} + 115$ хвилин для кожної активної ставки `paper_bets (PENDING)`.
   - Мета: негайне отримання фінального рахунку та розрахунок прибутку/збитку без кількагодинної затримки.
3. **BASELINE (Базовий моніторинг)**:
   - Час: раз на 3-4 години у денний час (09:00 – 21:00), якщо найближчих матчів немає.

### Б. Кластеризація (Debounce / Clustering)
* Якщо кілька матчів розпочинаються або закінчуються з різницею менше 25 хвилин — точки об'єднуються в один спільний запуск за 15 хвилин до найранішого матчу кластера, щоб уникнути спаму та зайвих витрат запитів.

### В. Збереження розкладу (Database Schema)
Створюється службова таблиця `scheduler_plan`:
```sql
CREATE TABLE IF NOT EXISTS scheduler_plan (
    id SERIAL PRIMARY KEY,
    target_time TIMESTAMPTZ NOT NULL,
    trigger_type TEXT NOT NULL, -- 'PRE_MATCH', 'SETTLE', 'BASELINE'
    event_ids TEXT[] DEFAULT '{}',
    description TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'PLANNED', -- 'PLANNED', 'EXECUTED', 'SKIPPED'
    executed_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_scheduler_target ON scheduler_plan (target_time, status);
```

## 3. Критерії приймання (Acceptance Criteria)

- **AC-1**: Функція аналізує найближчі матчі на горизонт 24–36 годин та формує список рекомендованих точок запуску.
- **AC-2**: Події з інтервалом $< 25$ хв об'єднуються в один кластер.
- **AC-3**: Для кожної незавершеної ставки з `paper_bets` планується точка розрахунку через 115 хвилин після початку.
- **AC-4**: Розклад зберігається в таблиці `scheduler_plan` (UPSERT або оновлення списку невиконаних точок).
- **AC-5**: Наприкінці зведення в Telegram додається блок із найближчими 2–3 критичними точками за київським часом.
- **AC-6**: Модуль може запускатися окремо для перегляду розкладу: `python scheduler.py --show`.
