# Специфікація: Монітор здоров'я та затримок планувальника (SPEC-09)

## 1. Контекст та проблема
GitHub Actions виконує заплановані задачі (`schedule: cron`) на базі черги з плаваючим пріоритетом. У години пікових навантажень (наприклад, у вихідні дні під час футбольних турів) запуск може затримуватись на 20–45 хвилин або зависати в черзі.
Для спортивного моніторингу така затримка є критичною: за 30 хвилин до матчу коефіцієнти можуть впасти на 20–30%, і якщо запуск запізнився, сигнал втрачає цінність.

## 2. Мета SPEC-09
Створити систему діагностики та захисту від "засинання" планувальника (**Watchdog & Healthcheck**):
1. Фіксація відмітки пульсу (`system_heartbeat`) під час кожного запуску системи.
2. Автоматичне виявлення запізнень черги та пропущених контрольних точок із таблиці `scheduler_plan`.
3. Сповіщення в Telegram у разі виявлення критичної затримки ($> 25$ хвилин) або падіння попереднього воркфлоу.
4. Підтримка зовнішнього пінгу (готовність до інтеграції з Healthchecks.io / UptimeKuma / зовнішнім вебхуком).

---

## 3. Схема даних (Database Schema)

```sql
CREATE TABLE IF NOT EXISTS system_heartbeat (
    service_name TEXT PRIMARY KEY,
    last_ping_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_status TEXT NOT NULL DEFAULT 'OK',
    last_duration_sec NUMERIC(6,2),
    metadata JSONB DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

---

## 4. Бізнес-правила та логіка Watchdog

### А. Фіксація пульсу (Heartbeat Ping)
* При успішному запуску та завершенні циклу записується поточний час `NOW()`, тривалість роботи скрипта в секундах, кількість знайдених прогрузів та статус `OK` або `WARNING`.

### Б. Виявлення пропущених точок розкладу (Missed Checkpoints)
* Watchdog звіряє поточний час із записами в `scheduler_plan`:
  ```sql
  SELECT id, target_time, description FROM scheduler_plan
  WHERE status = 'PLANNED' AND target_time < NOW() - INTERVAL '25 minutes';
  ```
* Якщо такі точки знайдено:
  - Статус оновлюється на `'MISSED'`.
  - Формується попередження для Telegram:
    `⚠️ <b>Увага: Затримка планувальника GitHub Actions!</b>`
    `Пропущено або затримано контрольну точку: <i>Перед грою: Chelsea - Arsenal</i> (планувалась на 18:45, затримка 35 хв).`

### В. Виявлення простою системи (Stale Heartbeat)
* Якщо різниця між поточним запуском і попереднім `last_ping_at` перевищує очікуваний інтервал (наприклад, $> 150$ хвилин у денний час з 08:00 до 23:00):
  - Фіксується інцидент «Простій системи» (можливе падіння GitHub Actions або зупинка розкладу).

---

## 5. Критерії приймання (Acceptance Criteria)

- **AC-1**: Таблиця `system_heartbeat` автоматично створюється та оновлюється при кожному запуску.
- **AC-2**: Функція `check_watchdog()` виявляє прострочені точки в `scheduler_plan` ($> 25$ хв) і переводить їх у статус `'MISSED'`.
- **AC-3**: Якщо знайдено прострочені точки або простій $> 150$ хв у денний час, надсилається окремий або інтегрований алерт у Telegram.
- **AC-4**: Модуль підтримує запуск як окремий CLI-інструмент `python watchdog.py --ping` / `python watchdog.py --status`.
- **AC-5**: Написано автотести для перевірки логіки детекції затримок без обов'язкового зв'язку з живою БД.
